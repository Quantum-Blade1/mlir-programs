\chapter{The DQC Dialect: Designing a Domain-Specific IR in MLIR}
\label{ch:mlir_compiler_architecture}

\begin{quote}
\textit{``Monolithic quantum compilers treat circuits as flat arrays of gates. To compile distributed quantum computers, we must elevate quantum semantics into a first-class Multi-Level Intermediate Representation with formal types, verifiable invariants, and progressive lowering.''}
\end{quote}

Quantum compiler engineering has historically suffered from the ``monolithic abstraction gap.'' Early frameworks (such as Qiskit Terra, Cirq, and Quil) represented quantum programs as Python-level Directed Acyclic Graphs (DAGs) or flat gate arrays. While adequate for 5-qubit single-chip experiments, these flat representations collapse under the demands of distributed quantum computing. A distributed compiler must simultaneously reason about:
\begin{enumerate}
    \item Unitary algebraic optimizations (gate cancellation, commutation rules),
    \item Partition topology and graph cut costs,
    \item Classical-quantum control flow (measurement-based feedforward fix-ups),
    \item Asynchronous message-passing runtimes (EPR distribution queues, MPI/RDMA transports), and
    \item Physical hardware pulse schedules and cryogenic memory lifetimes.
\end{enumerate}

No single abstraction level can capture these disparate concerns. This chapter details the design of the **DQC Dialect** built upon the **Multi-Level Intermediate Representation (MLIR)** and LLVM infrastructure. We formalize the TableGen dialect specification, custom quantum type systems, Linear Static Single Assignment (SSA) invariants, and hardware memory models.

The advantages of MLIR over traditional monolithic data structures include:
\begin{itemize}
    \item **Progressive Lowering:** Transformations occur across distinct semantic levels rather than in a single monolithic compiler pass, enabling verification at each boundary.
    \item **Declarative Op Definitions (ODS):** Operations, operand types, and side effects are defined declaratively in TableGen, generating C++ verifiers automatically.
    \item **Declarative Rewrite Rules (DRR):** Quantum algebraic patterns ($H \cdot H \to \mathbb{I}$, $X \cdot Z \to -iY$) are specified declaratively and compiled into optimized pattern matchers.
    \item **Native Coexistence of Classical and Quantum Semantics:** Classical loop counters, distributed memory pointers, and quantum state registers live within the same compiler basic block.
\end{itemize}

\section{Dialect Definition and TableGen Specifications}
\label{sec:tablegen_spec}
% ==============================================================================

In MLIR, dialects are formally defined using TableGen (\texttt{.td}) files. Below is the exact structural specification of the \texttt{dqc} dialect.

\subsection{Dialect Declaration}
\begin{lstlisting}[language=MLIR, caption={TableGen definition of the DQC Dialect (DQCDialect.td)}]
// DQCDialect.td - Root Dialect Definition
def DQC_Dialect : Dialect {
  let name = "dqc";
  let summary = "Distributed Quantum Computing Dialect";
  let description = [{
    The DQC dialect provides primitives for modeling, partitioning, 
    scheduling, and lowering distributed quantum circuits across 
    multi-QPU physical architectures.
  }];
  let cppNamespace = "::mlir::dqc";
  let useDefaultTypePrinterParser = 1;
}
\end{lstlisting}

\subsection{Custom Quantum Types}
Traditional LLVM IR operates on integers and floating-point registers. The DQC dialect introduces domain-specific first-class types:
\begin{enumerate}
    \item \texttt{!dqc.qubit}: Represents a physical or logical two-level quantum state handle.
    \item \texttt{!dqc.epr\_handle}: Represents an allocated entangled bipartite state shared between two QPUs.
    \item \texttt{!dqc.qpu\_id}: Represents a physical quantum processor identifier.
\end{enumerate}

\begin{lstlisting}[language=MLIR, caption={TableGen specification of custom DQC types}]
def DQC_QubitType : TypeDef<DQC_Dialect, "Qubit"> {
  let mnemonic = "qubit";
  let summary = "A quantum bit state handle";
}

def DQC_EPRHandleType : TypeDef<DQC_Dialect, "EPRHandle"> {
  let mnemonic = "epr_handle";
  let summary = "A non-local entangled Bell pair handle";
  let parameters = (ins "unsigned":$sourceQPU, "unsigned":$targetQPU);
  let assemblyFormat = "`<` $sourceQPU `,` $targetQPU `>`";
}
\end{lstlisting}

\subsection{Operation Declarations}
Operations in DQC are defined with strict operand and result invariants. Below is the specification of the fundamental non-local operation \texttt{dqc.telegate}:

\begin{lstlisting}[language=MLIR, caption={TableGen specification of the distributed Telegate operation}]
def DQC_TeleGateOp : DQC_Op<"telegate", [
    AllTypesMatch<["controlIn", "controlOut"]>,
    AllTypesMatch<["targetIn", "targetOut"]>
]> {
  let summary = "Synthesizes a distributed two-qubit gate via teleportation";
  let arguments = (ins 
    DQC_QubitType:$controlIn,
    DQC_QubitType:$targetIn,
    DQC_EPRHandleType:$eprPair,
    StrAttr:$gateType
  );
  let results = (outs 
    DQC_QubitType:$controlOut,
    DQC_QubitType:$targetOut
  );
  let assemblyFormat = [{
    $gateType $controlIn `,` $targetIn `using` $eprPair 
    attr-dict `:` type($controlIn) `,` type($targetIn) `,` type($eprPair)
  }];
}
\end{lstlisting}

\section{Linear Static Single Assignment (SSA) in Quantum Logic}
\label{sec:linear_ssa}
% ==============================================================================

A central innovation of the DQC dialect is its reconciliation of **Static Single Assignment (SSA)** with the **No-Cloning Theorem** of quantum mechanics.

\subsection{The Quantum Cloning Hazard in Classical SSA}
In classical SSA (e.g., standard LLVM IR), a computed value \texttt{\%x} can be read arbitrarily many times by downstream operations:
\begin{lstlisting}[language=MLIR]
// Classical SSA - Perfectly Legal (Value Duplication)
%x = arith.addi %a, %b : i32
%y1 = arith.muli %x, %c : i32
%y2 = arith.subi %x, %d : i32  // Multiple uses of %x
\end{lstlisting}

If applied naively to quantum registers, multiple reads of a qubit SSA value \texttt{\%q} would imply quantum state cloning:
\begin{lstlisting}[language=MLIR]
// ILLEGAL QUANTUM CODE: Violates No-Cloning Theorem!
%q_out1 = dqc.h %q : !dqc.qubit
%q_out2 = dqc.x %q : !dqc.qubit  // FATAL: Cloning %q!
\end{lstlisting}

\subsection{Linear Typing and Affine Value Semantics}
To guarantee physical validity, DQC enforces **Linear SSA Semantics**:
\begin{enumerate}
    \item Every quantum operation consumes its input SSA values and produces fresh output SSA values.
    \item An SSA value of type \texttt{!dqc.qubit} must have **exactly one consumer operation** in the dominance frontier.
    \item The MLIR operation verifier recursively inspects the \texttt{use\_empty()} status of consumed handles, raising a compilation error if an active qubit handle is referenced more than once.
\end{enumerate}

\section{Verifiable Dialect Invariants and Memory Layout}
\label{sec:dialect_invariants}
% ==============================================================================

At the C++ implementation level, the DQC compiler validates dialect invariants through custom C++ verification methods attached to each operation:

\begin{lstlisting}[language=C++, caption={C++ Op Verification Hook in DQCDialect.cpp}]
::mlir::LogicalResult TeleGateOp::verify() {
  auto eprType = getEprPair().getType().cast<EPRHandleType>();
  unsigned srcQPU = eprType.getSourceQPU();
  unsigned dstQPU = eprType.getTargetQPU();
  
  if (srcQPU == dstQPU) {
    return emitOpError("EPR handle must span distinct QPUs, but got src == dst == ") 
           << srcQPU;
  }
  
  // Verify that control and target qubits belong to disjoint partitions
  auto ctrlOwner = getQpuOwner(getControlIn());
  auto tgtOwner = getQpuOwner(getTargetIn());
  
  if (ctrlOwner != srcQPU || tgtOwner != dstQPU) {
    return emitOpError("Telegate QPU mapping mismatch: control belongs to QPU ")
           << ctrlOwner << ", expected " << srcQPU;
  }
  
  return ::mlir::success();
}
\end{lstlisting}

These compile-time verification passes ensure that by the time the circuit reaches target lowering, every non-local gate has verified QPU mappings, valid linear SSA lifetimes, and guaranteed physical hardware routability.
